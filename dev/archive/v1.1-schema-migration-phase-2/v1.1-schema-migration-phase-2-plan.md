## API Specifications

No new HTTP routes (FR-HTTP-2's read-only route list is unchanged by this
phase). One response-model field addition:

**`GET /stats/task/{task_id}?since=`** (`plumb/http.py` → `_http_stats.py::compute_task_stats` → `_http_schemas.py::StatsOut`)

- **Response schema delta:** `StatsOut` gains `dollar_cost_run_count: int` (FR-STATS-1). `StatsOut` has `model_config = ConfigDict(extra="forbid")`, so the field must be declared explicitly — a silently-added dict key would not survive Pydantic validation, which is the mechanism this TRS relies on to catch a missed wiring step.
- **Error handling:** unchanged — `NotFoundError` (the existing `_http_stats.py`-local one, for empty windows) still maps to HTTP 404 via the existing FastAPI exception handler; this phase does not touch that path.
- **Auth / rate limiting:** unchanged — loopback-only, no auth, no rate limiting (NFR-Sec-4, unchanged by this phase).
- **Backward compatibility:** additive field on a versioned response; existing clients that don't read the new field are unaffected. Clients pinned to a strict schema (rare, but `extra="forbid"` on the *client* side would break) are out of scope — plumb does not control client-side schemas.

No public-API routes for `set_usage`, `add_example`, `resume_run`, `attributes`, or `idempotency_key` — these are library/CLI surface only (FR-API-1/4 renegotiation is a Python-callable change, not an HTTP route change).

## Database Design

### Schema details

**Migration `user_version` 1 → 2** (DATA-MIG-2), applied as one transaction inside `_bootstrap_schema`:

```sql
ALTER TABLE scores ADD COLUMN rationale TEXT;                          -- §15.4
ALTER TABLE spans  ADD COLUMN tokens_in INTEGER;                       -- §15.5
ALTER TABLE spans  ADD COLUMN tokens_out INTEGER;                      -- §15.5
CREATE UNIQUE INDEX idx_scores_idem
    ON scores(run_id, metric_name, scorer_version, IFNULL(span_id, '')); -- §15.6
ALTER TABLE spans  ADD COLUMN attributes TEXT;                          -- §15.8
```

No `ALTER` for Feature 6 (`set_usage`) — `runs.tokens_in`, `runs.tokens_out`,
`runs.dollar_cost` already exist in the v1.0 DDL (`_schema.py` runs table);
this phase only starts writing them on the online path.

**Relationships/constraints:** unchanged — all five DDL changes are additive
columns/index on the four existing tables (`runs`, `spans`, `scores`,
`examples`). No new table (four-table thesis intact, DATA-MIG-3). No FK
changes. No CHECK constraint changes (STRICT-table typing is unaffected by
`ADD COLUMN`).

**Indexes:** `idx_scores_idem` is the only new index — UNIQUE, NULL-safe via
`IFNULL(span_id,'')` (FR-IDEM-1). No new index for `tokens_in`/`tokens_out`
or `attributes` (attributes is explicitly not promised indexed aggregation —
§15.8 "Known trade").

### Data access patterns

- **`_FINALIZE_RUN` UPDATE** (`storage_sqlite.py:291-303`) gains three
  `SET` clauses (`tokens_in = ?`, `tokens_out = ?`, `dollar_cost = ?`) fed
  from `finalize_run`'s three new kwargs. Still one UPDATE per run close
  (NFR-Perf-2 budget unaffected — NFR-USAGE-1).
- **`_INSERT_SPAN`** gains `tokens_in`, `tokens_out`, `attributes` columns.
  `_span_to_row` continues to also populate the legacy `tokens` sum column
  (FR-TOKENS-2) — three token-bearing columns written per span row
  post-migration, one write, no extra query.
- **`_INSERT_SCORE`** gains `rationale`. `write_score` gains an idempotent
  path: `INSERT ... ON CONFLICT (run_id, metric_name, scorer_version,
  IFNULL(span_id,'')) DO NOTHING` (FR-IDEM-2), returning whether the row was
  actually inserted (needed so `RunHandle.add_score` / `plumb score write`
  can report insert-vs-no-op to the caller per FR-IDEM-2).
- **`open_or_resume(run_id)`** (new): `SELECT * FROM runs WHERE run_id = ?`;
  raise `NotFoundError` if no row; raise `ValidationError` if
  `status NOT IN ('pending')` — a run opened via `plumb.run()` is inserted as
  `status='pending'` at `__enter__` and only becomes terminal at `__exit__`
  (see `_INSERT_PENDING_RUN` / `open_run` in `storage_sqlite.py:409-429`). So
  the resumable state is `status = 'pending'`; anything in
  `('success','failure','aborted')` is terminal and MUST raise
  `ValidationError` (FR-RESUME-2). `'stalled'` is also treated as
  terminal-for-this-purpose in this TRS's design (it was `pending` but timed
  out — resuming it would race the stalled-sweep) — **this is a judgment call
  beyond what §15.1 states explicitly**, flagged in the tasks file's Pending
  Decisions.
- **Aggregation SQL** (`aggregate_runs_for_task`, `storage_sqlite.py:719-788`):
  add `COUNT(dollar_cost) AS dollar_cost_run_count` to the existing `SELECT`
  that already computes `COUNT(*) AS run_count` and `SUM(dollar_cost) AS
  dollar_cost_total` (FR-USAGE-6) — one more column in the same query, no new
  query, no new index (NFR-USAGE-2).
- **Token auto-fill** (FR-USAGE-3): at `finalize_run` time, if the caller's
  `tokens_in`/`tokens_out` kwargs are both `None` (i.e. `set_usage` never
  supplied them), sum the **already-buffered in-memory** `spans` list's
  `tokens_in`/`tokens_out` fields (post-§15.5 split values only — spans with
  `tokens_in is None` are excluded from the sum per FR-TOKENS-3/FR-USAGE-3
  "legacy spans MUST NOT guess"). This happens in `_RunFactory.__exit__`
  or inside `finalize_run` itself before the UPDATE — **no additional SELECT**
  (NFR-USAGE-2).

### Migration strategy

Sequencing inside `_bootstrap_schema`'s new `1 → 2` arm (DATA-MIG-5), all in
one transaction (DATA-MIG-4):

1. **Duplicate pre-check** (DATA-MIG-6) — `SELECT run_id, metric_name,
   scorer_version, IFNULL(span_id,'') AS span_key, COUNT(*) FROM scores
   GROUP BY run_id, metric_name, scorer_version, span_key HAVING COUNT(*) > 1`.
   If any rows return, **abort the whole migration** with `StorageError`
   naming every conflicting tuple + count. `user_version` stays `1`. Zero
   rows deleted (NFR-Rel-4).
2. Run the four `ALTER TABLE` statements + the one `CREATE UNIQUE INDEX`
   (order matters only in that the index requires the pre-check to have
   already passed — the `ALTER`s and the index can run in any order relative
   to each other since none of the four `ALTER`s touch `scores`' uniqueness).
3. `PRAGMA user_version = 2`.
4. Commit. On any exception in steps 1–3, roll back; `user_version` stays `1`
   (DATA-MIG-4, AC-MIG-4).
5. Re-run guard: if `user_version == 2` already, skip the whole arm — no-op
   (AC-MIG-2).

**Rollback strategy:** the migration is forward-only; there is no `2 → 1`
downgrade path (DATA-MIG-5 — a database at `user_version > SCHEMA_VERSION`
raises `StorageError`, "downgrade is unsupported"). The only rollback is the
in-transaction abort described above, which restores `user_version=1` with
the pre-migration schema untouched — this is a **migration-attempt** rollback,
not a **data** rollback; user backup/restore (DATA-BAK-1) is the only path to
undo a *committed* migration.

## Algorithm & Logic Design

### `resume_run` open/close (FR-RESUME-1..5)

```
def resume_run(run_id):
    _init_storage_singletons()
    run_row = storage.open_or_resume(run_id)     # raises NotFoundError if absent
    if run_row.status != 'pending':
        raise ValidationError(f"run {run_id} is already terminal ({run_row.status})")
    builder = _RunBuilder(run_id=run_id, task_id=run_row.task_id, kind=run_row.kind,
                           parent_run_id=run_row.parent_run_id, start_ts=run_row.start_ts,
                           # carry forward existing model/version fields so a
                           # resumed set_models() call still last-wins correctly
                           orchestrator_model=run_row.orchestrator_model, ...)
    handle = RunHandle(builder)
    token = _active_run.set(handle)
    yield handle
    # on exit: identical finalize path to _RunFactory.__exit__ (FR-RESUME-3) —
    # re-uses the SAME finalize_run() UPDATE-not-INSERT, since the row already
    # exists (open_run's INSERT already happened in the original process).
```

Key invariant carried over from `_RunFactory`: `finalize_run` is already an
`UPDATE ... WHERE run_id=?` (not INSERT) — §15.1's storage contract note
("adapter grows an `open_or_resume(run_id)` path ... whose `finalize_run`
performs an UPDATE") is **already true of the existing `finalize_run`**; the
only new adapter method is the `SELECT` + status-check in `open_or_resume`.
This significantly de-risks Feature 1 — no new write path, only a new read +
validate path plus reusing the existing finalize machinery.

### Token auto-fill precedence (FR-USAGE-3, pseudocode)

```
def compute_run_level_tokens(explicit_tokens_in, explicit_tokens_out, buffered_spans):
    if explicit_tokens_in is not None or explicit_tokens_out is not None:
        # explicit wins per-field; no merge with auto-fill (AC-USAGE-3)
        return explicit_tokens_in, explicit_tokens_out
    eligible = [s for s in buffered_spans if s.tokens_in is not None]  # excludes legacy-shape spans
    if not eligible:
        return None, None
    return (sum(s.tokens_in or 0 for s in eligible),
            sum(s.tokens_out or 0 for s in eligible))
```

Note: "legacy spans excluded" here means spans **within the same in-memory
buffer** that somehow lack a split (shouldn't normally happen for spans
written in the same process post-migration, but `add_span(tokens=(in,out))`
always populates both, so in practice this guards a pathological caller
passing `tokens=None`, i.e. a span with no token data at all — not the
DB-level v1.0 legacy-row case, which is about *stored* rows, not *buffered*
ones). This distinction matters because FR-TOKENS-3/FR-USAGE-3's "legacy
spans MUST NOT guess" text is about **already-persisted** v1.0 rows being
read back, which never enters this in-memory auto-fill path at all (auto-fill
only sees the current run's freshly-buffered spans, never historical ones).

### Idempotent score write (FR-IDEM-2..4, pseudocode)

```
def write_score(score, idempotency_key=None):
    # idempotency_key is advisory only (FR-IDEM-4) — not stored, not part of
    # the conflict target. The UNIQUE index IS the authority.
    cur = conn.execute(
        "INSERT INTO scores (...) VALUES (...) "
        "ON CONFLICT(run_id, metric_name, scorer_version, IFNULL(span_id,'')) DO NOTHING"
    )
    return cur.rowcount == 1   # True = inserted, False = no-op (row already existed)
```

## Error Handling & Edge Cases

| Case | Behaviour | Governing req |
| --- | --- | --- |
| `resume_run(run_id)` where `run_id` doesn't exist | raise `NotFoundError` before yielding, no row written | FR-RESUME-4, AC-RESUME-3 |
| `resume_run(run_id)` where run is already terminal | raise `ValidationError` before yielding, no row written | FR-RESUME-2, AC-RESUME-2 |
| `resume_run(run_id)` where run is `stalled` | raise `ValidationError` (treated as terminal-for-resume; see Pending Decisions) | judgment call — flagged |
| `add_example` with malformed hash | raise `ValidationError`, no `examples` row | FR-ADDEX-3, AC-ADDEX-2 |
| `set_usage(...)` after `abort()` | no-op, same as `add_span`/`add_score` post-abort | FR-USAGE-5 |
| storage failure on `set_usage`/`add_example`/`resume_run` write | fail-degrade, WARNING log, never raise into caller (except the two pre-yield raises above, which are caller errors, not plumb-internal failures) | NFR-Rel-1, NFR-RESUME-2 |
| `add_span(attributes=<non-JSON-serializable>)` | raise `ValidationError` at API boundary, no span row written | FR-ATTR-3 (D-b1 fail-closed-on-write), AC-ATTR-3 |
| reading a legacy span with malformed/absent `attributes` | surfaces as `None`, never raises | FR-ATTR-3 (never raise on read), NFR-Rel-1 |
| `attributes` payload > soft cap (~8KB serialized) | raise `ValidationError` on write | FR-ATTR-4 |
| migration finds duplicate score rows under the new unique key | abort whole migration, `StorageError` naming tuples + count, zero deletions, `user_version` stays 1 | DATA-MIG-6, AC-MIG-3 |
| migration fails partway (any step) | full rollback, `user_version` stays 1, no partial column added | DATA-MIG-4, AC-MIG-4 |
| re-open an already-migrated DB | no-op, no error | DATA-MIG-3, AC-MIG-2 |
| DB at `user_version > 2` (newer plumb wrote it) | raise `StorageError`, downgrade unsupported | DATA-MIG-5 |
| `set_usage(dollar_cost=...)` never called | `runs.dollar_cost` stays `NULL` — never fabricated | FR-USAGE-3, FR-USAGE-3a, AC-USAGE-2 |
| two spans, no `set_usage`, tokens auto-fill | `runs.tokens_in/out` = sum of buffered spans' split fields | FR-USAGE-3, AC-USAGE-2 |
| `set_usage(tokens_in=X)` + spans also present | explicit `X` wins, no merge/sum with span totals | FR-USAGE-3 precedence, AC-USAGE-3 |
| idempotent `add_score` retried with identical semantic key | exactly one row exists; second call reports no-op | FR-IDEM-2, AC-IDEM-1 |
| judge fail-open error row (`scorer_version` ending `:error`) followed by a real re-score | both rows coexist — distinct keys, error doesn't block re-score | FR-IDEM-3, AC-IDEM-2 |

**Retry strategy:** none of this phase's new writes are network calls (all
local SQLite) — no retry/backoff logic is introduced. The existing
INT-JUDGE-5 retry-with-backoff for judge HTTP calls is unaffected.

**Fallback mechanisms:** legacy-row fallbacks (FR-TOKENS-3, FR-ATTR-5,
FR-RATIONALE-3) are all "surface as `NULL`/pre-migration value, never
fabricate" — consistent fallback posture across all three new nullable
columns.

## Security Considerations

- **Input validation:** `attributes` dict MUST be validated JSON-serializable
  and size-capped at the API boundary (`add_span`), not at the storage layer
  — fail fast, no partial write (FR-ATTR-3/4). `inputs_hash`/
  `expected_output_hash` in `add_example` reuse the existing `_require_hex64`
  validator from `core/entities.py` (no new validation logic to write).
- **SQL injection prevention:** all new SQL (the `ON CONFLICT` write path,
  the duplicate pre-check `GROUP BY`, the `dollar_cost_run_count` aggregate,
  `open_or_resume`'s `SELECT`) MUST use parameterized queries exclusively
  (NFR-Sec-3, ruff `S608`) — consistent with every existing query in
  `storage_sqlite.py`.
- **No new secrets/credentials surface** — this phase touches no judge
  adapter, no HTTP auth, no env var additions beyond what's already covered
  by `pydantic-settings` (NFR-Sec-1 unaffected).
- **`idempotency_key` is advisory, not authoritative** (FR-IDEM-4) — it must
  not be treated as a security boundary or dedup guarantee on its own; the
  UNIQUE index is the actual enforcement. Document this explicitly in the
  docstring so a future caller doesn't rely on the key for correctness.
- **Migration abort-on-duplicate is a deliberate security/integrity choice**
  (DATA-MIG-6) — never auto-delete user data to satisfy a new constraint.

## Testing Strategy

Per TRD §10.1 test pyramid (unit ≥90% on `plumb/core/`, integration ≥80% on
`plumb/adapters/` + `plumb/api.py`, overall ≥75%), extended for this phase:

- **Unit (`tests/unit/core/`):** `Span.attributes` round-trip at the entity
  level (dict in → dict out, no JSON logic at this layer — that's the
  adapter's job); `core/errors.py::NotFoundError` importable and subclasses
  `PlumbError`; XOR-style validation for any new entity field is exercised
  via Hypothesis where an existing property test already covers the entity
  (extend, don't duplicate).
- **Unit (`tests/unit/api/`):** `RunHandle.add_example`/`set_usage` buffering
  semantics against `FakeStorageWriter` — last-non-None-wins for `set_usage`,
  no-op after `abort()` for both, `add_example` hash validation raising
  before any fake-writer call.
- **Integration (`tests/adapters/` or `tests/integration/`):** real
  temp-file SQLite for every AC-MIG-* case (migration idempotence, duplicate
  abort, transactional rollback) — these are exactly the kind of test that
  must NOT run against `:memory:` alone, since `user_version` persistence and
  multi-run reopen semantics need a real file. `open_or_resume` cross-call
  behavior (two sequential `SQLiteStorageAdapter` instances against the same
  file, simulating cross-process resume) belongs here too.
- **Property (Hypothesis):** extend the existing schema-invariant property
  suite to cover `idx_scores_idem` — generate random `(run_id, metric_name,
  scorer_version, span_id)` tuples with intentional collisions and assert
  exactly one row survives per semantic key.
- **E2E (`tests/e2e/`):** one new scenario extending the existing reference
  E2E (toy orchestrator + sub-agents) to (a) resume a run from a second
  simulated process, (b) call `set_usage` + auto-fill tokens, (c) attach
  `attributes` to a span, (d) promote an `add_example` from inside the run —
  asserting the full row set lands correctly post-migration.
- **Regression (critical, per §18 Phase 2 exit criteria):** re-run the full
  §13 v1.0 acceptance-criteria suite against a **migrated** database (open a
  v1.0-shaped DB fixture, let `_bootstrap_schema` migrate it, then run every
  existing v1.0 test against the migrated file) to prove zero regression.
  This is new test *infrastructure* (a migrated-DB fixture), not new test
  *cases* — see the tasks file's dedicated task for this.
- **Mocking policy:** unchanged from §10.5 — no real judge HTTP calls, no
  real filesystem beyond `tmp_path`, `freezegun` for timestamp assertions
  where `resume_run`'s `start_ts`-preservation is checked.

## Performance Considerations

All performance budgets are stated as NFRs in TRD §15.9 and are inherited
as-is by this TRS — no new budget is invented here:

- **NFR-MIG-1:** migration ≤ 500ms for ≤100k score rows; duplicate pre-check
  (an indexed `GROUP BY ... HAVING COUNT(*)>1` scan) is the dominant cost.
  Reference-benchmark this in the migration integration test with a
  synthetic 100k-row fixture (new perf-adjacent test, not in `tests/perf/`
  since it's a one-shot cost not a hot-path budget — place under
  `tests/integration/`).
- **NFR-USAGE-1/2:** `set_usage` + token auto-fill + coverage count add zero
  additional queries to the existing finalize/aggregate paths — verify by
  asserting query *count* (not just wall-clock) in a targeted test, e.g. via
  a connection-execute counter fixture, so a future refactor can't silently
  regress this into an N+1. The existing NFR-Perf-2 budget (≤50ms run-close
  for ≤100 spans) is the regression guard — re-run
  `tests/perf/test_span_overhead.py` post-migration to confirm no drift.
- **NFR-RESUME-1:** `resume_run` open adds ≤5ms p95 over `run()`'s existing
  open path — needs a dedicated micro-benchmark alongside
  `tests/perf/test_span_overhead.py` (same harness style, new file).
- **`json_extract` over `attributes`:** explicitly *not* promised indexed
  performance (§15.8 "Known trade") — no NFR to satisfy here, just don't
  accidentally add an index that contradicts the documented trade.
