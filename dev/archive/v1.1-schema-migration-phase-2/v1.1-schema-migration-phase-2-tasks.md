    `(run_id, metric_name, scorer_version, span_id)` tuple + row count before
    any `ALTER` runs. Wrap the whole arm (pre-check + 5 DDL statements +
    `PRAGMA user_version=2`) in one transaction (DATA-MIG-4).
  - **Acceptance Criteria:**
    - [ ] AC-MIG-1: v1.0 `user_version=1` DB opened by this build → `user_version=2`, all 5 new schema objects (`rationale`, `tokens_in`, `tokens_out`, `idx_scores_idem`, `attributes`) exist, all pre-existing rows readable unchanged.

  - **Files to Create/Modify:**

    - `plumb/adapters/storage_sqlite.py` - `_bootstrap_schema` 1→2 arm, duplicate pre-check query, transactional wrapper.
  - **Dependencies:** none (this is the spine task; everything else depends on it).

## Pending Decisions & Clarifications

Implementation-level judgment calls this TRS had to make because TRD §15
doesn't state them explicitly. None re-open a TRD-level decision — D-a1,
D-a2, D-b1, D-b2, D-b3 are all settled in TRD §15/TRD-v2. These are narrower
than that, and are flagged here rather than silently assumed:

1. **Is a `stalled` run resumable via `resume_run`?** §15.1's FR-RESUME-2
   only says "already-terminal (`success`/`failure`/`aborted`)" must raise.
   It doesn't mention `stalled` (a fourth non-`pending` state, set by the
   1-hour stalled-sweep, FR-EDGE-2). This TRS's Task 6 design treats
   `stalled` as **also non-resumable** (raise `ValidationError`), reasoning:
   resuming a run the stalled-sweep already gave up on would race the sweep
   and contradicts its purpose.

   - **(a) Treat `stalled` as non-resumable** (this TRS's default) — simplest, avoids a race with the sweep, but means a resumed cross-process run that takes >1 hour to hand off becomes permanently unresumable.
   - **(b) Treat `stalled` as resumable** (only `success`/`failure`/`aborted` block) — matches FR-RESUME-2's literal text, but risks a `resume_run` call racing a concurrent sweep marking the same row `stalled` mid-resume.
   - **(c) Make the stalled-threshold configurable and document that atlas's expected hand-off latency must stay under it** — punts the problem to configuration rather than code.

   Recommend **(a)** as the safer default given NFR-RESUME's cross-process
   safety note already documents "concurrent access is an unsupported caller
   pattern" — but this should be confirmed before Task 6 is implemented,
   since it's user-visible behavior not spelled out in the normative FRs.

2. **`write_score` return type: `bool` (inserted-or-not) vs. `str`
   (`score_id`, possibly of the pre-existing row on conflict)?** FR-IDEM-2
   only says "the method MUST return a flag or the existing `score_id`."
   This TRS's Task 5 recommends `bool` for `write_score` at the adapter
   layer (simplest, avoids a second SELECT to fetch the existing row's ID on
   conflict) while `RunHandle.add_score` keeps returning the `score_id` it
   already generated client-side (which is correct in the insert case and
   merely "the ID that *would* have been used" in the no-op case — the
   caller doesn't need the winning row's actual ID for idempotency purposes,
   only to know whether it won).

   **If a caller does need the winning row's actual `score_id` on conflict,
   that requires an extra `SELECT`** — flagging this trade-off for
   confirmation before Task 5 implementation locks it in.

3. **Migration DDL statement ordering within the single transaction.**
   DATA-MIG-2 lists the five statements in a specific order (rationale,
   tokens_in, tokens_out, idx_scores_idem, attributes) but doesn't assert
   this order is load-bearing beyond "the duplicate pre-check must precede
   the index creation." This TRS assumes the pre-check-before-index
   constraint is the *only* ordering requirement and the four `ALTER TABLE`
   statements are mutually order-independent (verified: none of the four
   `ALTER`s touch `scores`' uniqueness, so no ordering conflict exists
   between them) — no decision needed here, stating it for completeness
   since it's the kind of assumption a future session might otherwise
   silently re-derive differently.
